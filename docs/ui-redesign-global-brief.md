# EasySearch UI 重设计总体需求文档

## 文档目的

这份文档用于提供给其他 AI 或设计师，作为重新设计 EasySearch iOS 应用 UI 的功能性输入。

要求如下：

- 只描述产品需要支持的功能、信息组织方式和交互目标。
- 不继承、不复述、不参考现有 UI 的布局、风格、配色、组件形态或页面结构。
- 本文档只覆盖全局层设计，不展开任何具体业务模块的内部页面方案。

## 产品定位

EasySearch 是一个面向个人高频使用场景的 iOS 多功能效率工具应用。

它的整体角色不是单一工具，而是一个统一入口，承载以下几类能力：

- 一个高频、低门槛、可快速执行的核心入口能力。
- 多个相互独立、可持续扩展的功能模块。
- 一套统一的配置、通知、同步、权限和隐私管理体系。

重设计时，应把它理解为“轻量多功能个人工作台”，而不是单一页面或单一任务型应用。

## 总体设计目标

新 UI 需要满足以下目标：

- 用户进入应用后，能够迅速理解“我现在可以做什么”。
- 高频操作应具备最短路径，避免层级过深或入口分散。
- 多个功能模块需要被清晰组织，但不能让整体看起来像杂乱的功能堆叠。
- 全局配置、系统状态和账户状态要能被统一感知，而不是散落在各处。
- 应用需要保留后续继续新增功能的空间，新的能力加入后不应破坏整体结构。
- 应用需要兼顾普通功能与低曝光、受保护功能的共存。
- 所有关键状态都需要可见，包括未配置、未授权、离线、同步中、失败、空数据、后台处理中等状态。

## 全局功能范围

### 1. 应用级入口组织

应用在全局层必须提供三类一级能力：

- 核心高频入口：用于承载用户最常使用、最需要快速触达的主能力。
- 功能集合入口：用于承载多个独立功能模块的发现、进入、排序和扩展。
- 全局设置入口：用于承载所有跨模块配置、账户、同步、权限、通知和关于信息。

重设计可以自由定义这三类入口的表现形式，但必须保证：

- 用户能稳定找到这三类入口。
- 用户能清楚区分“执行功能”“浏览全部能力”“调整系统配置”这三种目的。
- 不同入口之间切换时，当前上下文不会轻易丢失。

### 2. 全局信息架构

应用整体信息架构需要支持以下对象：

- 应用级入口。
- 功能模块集合。
- 单个模块入口信息。
- 全局设置项。
- 账户与连接状态。
- 通知与后台任务状态。
- 同步状态。
- 隐私相关入口与受保护内容状态。

其中，单个模块在全局层只需要具备以下基础信息：

- 名称。
- 简述。
- 入口标识。
- 当前状态摘要。
- 是否需要额外配置或授权。
- 是否属于普通曝光能力或低曝光能力。

## 全局交互需求

### 1. 能力发现与进入

应用需要支持用户快速发现可用能力，并从全局层进入目标功能。

全局层必须支持：

- 查看所有已启用能力。
- 理解每个能力的大致用途。
- 识别哪些能力当前可直接使用，哪些能力还需要配置。
- 进入某个能力后，再返回到全局层时保留合理的浏览连续性。

### 2. 模块组织与扩展性

应用需要支持多个独立模块长期共存，且模块数量未来可能继续增加。

因此全局层必须支持：

- 模块的稳定归档和管理。
- 模块顺序或优先级管理。
- 新模块加入后可被自然纳入整体结构。
- 部分模块处于隐藏、受保护或低曝光状态。

### 3. 状态感知与反馈

全局层必须统一表达以下状态，而不是交给模块自行各自处理：

- 首次使用状态。
- 尚未完成配置。
- 尚未授予系统权限。
- 当前无数据。
- 正在同步或后台处理中。
- 网络不可用或远程服务不可用。
- 操作失败但可恢复。
- 需要用户进一步处理的提醒或待办状态。

用户在不进入具体模块的前提下，也应该能感知哪些地方需要处理。

### 4. 设置与配置管理

应用需要有统一的全局设置体系，用来管理跨模块配置。

全局设置层至少要容纳以下类型的信息：

- 账户或登录状态。
- 云端同步相关配置与状态。
- 第三方服务连接状态。
- AI 能力相关配置状态。
- 系统通知权限状态。
- 与具体模块相关但需要集中呈现的配置摘要。
- 版本与应用基础信息。

重设计时要保证：

- 用户知道“去哪里完成配置”。
- 用户能在设置层看见当前是否已经配置完成。
- 各模块的配置摘要具备统一表达逻辑。

### 5. 隐私与低曝光能力

应用需要支持一部分不适合高曝光展示的能力或内容。

全局层必须考虑：

- 低曝光能力默认不应与普通能力完全等价展示。
- 某些内容在应用切后台、切换场景或离开特定上下文时，需要进入保护状态。
- 用户重新回到应用时，受保护内容不应被无意暴露。
- 低曝光入口与普通入口需要在产品结构上共存，但不互相干扰。

### 6. 跨模块连续性

尽管各模块相互独立，但全局层仍需提供统一体验：

- 统一的返回逻辑。
- 统一的状态提示方式。
- 统一的待配置、异常、提醒信息表达方式。
- 统一的入口信息密度规则。
- 统一的“从提醒跳转到相应处理位置”的能力。

## 设计约束

其他 AI 在设计时必须遵守以下约束：

- 不要复用或推测当前产品已有页面结构。
- 不要预设具体导航样式、卡片样式、列表样式、标签样式或色彩风格。
- 不要先设计具体模块内部页面。
- 先解决应用级结构、入口组织、状态体系和配置体系。
- 必须为未来新增模块预留空间。
- 必须考虑 iPhone 场景下的单手操作和高频快速进入。
- 必须考虑存在后台刷新、通知、同步和远程连接状态的产品特性。
- 必须考虑存在部分敏感或低曝光能力的产品特性。

## 给其他 AI 的输出要求

如果基于本文档继续产出 UI 重设计方案，第一阶段只需要输出以下内容：

- 应用级信息架构方案。
- 一级入口组织方案。
- 全局导航与跨页面切换逻辑。
- 模块集合页的组织原则。
- 全局状态系统方案。
- 设置与配置中心的结构方案。
- 隐私与低曝光能力的全局处理方案。

暂时不要输出以下内容：

- 具体模块内部页面设计。
- 具体视觉风格稿。
- 现有页面的改版对照。
- 任何基于当前 UI 的局部微调方案。

## 验收标准

当其他 AI 基于这份文档产出总体 UI 方案时，该方案应满足：

- 不看现有界面也能独立成立。
- 只从功能与结构出发，而不是从现有页面出发。
- 能解释应用为何需要多个一级入口。
- 能解释多模块产品如何避免杂乱。
- 能解释配置、同步、通知、权限、隐私如何在全局层统一表达。
- 能为后续展开各模块设计留下清晰接口。
